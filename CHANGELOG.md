# Changelog

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — [SemVer](https://semver.org/lang/ru/).

## [Unreleased]

### Added

- Экспериментальный mod `mods/limit-alerts-status/` — отдельный плагин на
  TypeScript-хуках Claude Code с командой `/limits`: сводка по всем окнам,
  времени сброса и источнику данных печатается сразу, без хода модели и без
  токенов, в том числе посреди хода. Показывает и паузу монитора после ответа
  429. Как и statusline, для каждого окна берёт более свежую цифру — из ответа
  API этой сессии или из кэша монитора — и говорит, откуда взято каждое. В
  плагин `limit-alerts` и в marketplace не входит: API модов пока в early
  access. Запуск: `claude --plugin-dir mods/limit-alerts-status`.
  В версии 0.3.0 `/limits` показывает то же, что `status` 0.10.0: темп и
  недоиспользование недельных окон, расход по продуктам, платные credits.

### Fixed

- Цифры одного аккаунта могли записаться под другим: аккаунт брался из
  `~/.claude.json`, а данные приходили по токену из Keychain, и сразу после
  смены аккаунта эти два источника какое-то время расходятся. Отсюда ложные
  ♻️ «окно сброшено» и повторные предупреждения. Теперь аккаунт определяется
  по самому токену — один запрос к `/api/oauth/profile` на каждый новый токен
  (несколько в сутки); ответ запоминается под хешем токена, сам токен нигде не
  сохраняется и не попадает в список процессов. `doctor` показывает, если
  токен и `~/.claude.json` расходятся.
- Если `~/.claude.json` не удавалось прочитать (Claude Code постоянно его
  переписывает), проверка писала кэш без метки аккаунта, и его считал своим
  любой аккаунт — statusline, `status` и `/limits` могли показывать чужие
  цифры. Теперь чтение повторяется, а пока аккаунт неизвестен, проверка ничего
  не записывает. Кэш без метки показывается только установке вообще без входа.

## [0.11.4] - 2026-10-25

### Fixed

- В русском `status` колонки процентов разъезжались: встроенный в macOS
  bash 3.2 выравнивал подписи по байтам, а буква кириллицы — два байта, так

## [0.11.3] - 2026-10-24

### Fixed

- Сессии, открытые до обновления плагина, продолжали выполнять проверки
  своей старой версии: переписывали общее состояние в старом виде (из-за
  этого ⏳ и ⌛ могли прийти повторно) и следовали старым правилам паузы.
  Теперь хуки такой сессии ничего не делают — проверяют фоновый агент и
  сессии, открытые после обновления, — а `doctor` просит перезапустить
  старые сессии.
- После ответа 429 пауза сбрасывалась первым же успешным запросом и
  каждый раз начиналась заново с 5 минут: endpoint отказывал почти каждые 6
  минут часами. Теперь в течение часа после отказа пауза помнится и
  удваивается, а после успешного запроса следующий делается не раньше чем
  через 5 минут.

## [0.11.2] - 2026-10-24

### Fixed

- Ложные «♻️ Лимит сброшен» посреди окна — например, «Неделя: было 97%,
  сейчас 26%» за пять дней до сброса — и повторные 🟡/🔴 после них. Такие
  цифры приходят из другого источника: токена другого аккаунта или сессии,
  которая ещё работает на старой версии плагина. Окно не может закончиться
  раньше своего времени сброса, поэтому теперь это не считается сбросом:
  уведомления нет, а следующее пересечение порога по-прежнему приходит.
- Пустой или повреждённый файл состояния (например, после прерванной записи)
  навсегда выключал все уведомления. Теперь такой файл начинается заново, а
  записывается целиком через временный файл.

## [0.11.1] - 2026-10-24

### Fixed

- `doctor` в строке «Последняя неудачная проверка» показывал не причину, а
  следствие: «fallback unavailable…» — что не помогли и локальные данные
  Claude Code. Теперь он называет саму причину, например ответ HTTP 429.
- `doctor` писал «2 замеров» — теперь «1 замер», «2 замера», «5 замеров»
  (и «1 reading» по-английски).
- Во время паузы после 401/403/429 простаивающая statusline каждые ~30
  секунд запускала фоновую проверку: запросов она не делала, но каждый раз
  писала в лог «fallback unavailable». Теперь в паузе проверка запускается,
  только если в локальных данных Claude Code появилось что-то новее кэша —
  у аккаунтов, которым endpoint отказывает, это и есть источник цифр.

## [0.11.0] - 2026-10-24

### Added

- Напоминание ⌛ о неиспользованном лимите: подписка оплачена, даже если
  простаивает. В последние сутки перед сбросом недели, если при нынешнем
  темпе пропадёт 20 пунктов и больше, приходит одно уведомление — «40%, сброс
  сб 10:00 — при таком темпе ~55% останется неиспользованным», пока ещё есть
  время потратить остаток. Выключается опцией плагина `unused_alert`,
  `install.sh --no-unused-alert` или `UM_UNUSED_ALERT=0`.
- Вопрос перед субагентом (выключен по умолчанию): когда недельный лимит
  дошёл до 95%, запуск субагента сначала спрашивает подтверждение — субагенты
  тратят неделю быстрее всего, а кончившаяся неделя останавливает работу на
  дни. Решение остаётся за пользователем. Лимит по модели учитывается, только
  если субагенту явно задана эта модель. Включается опцией плагина
  `guard_fanout`, `install.sh --guard-fanout` или `UM_GUARD_FANOUT=1`.
- Подсказка сменить модель (выключена по умолчанию): к 🔴 о недельном лимите
  по модели добавляется «↪ Можно продолжить на другой модели (/model): этот
  лимит она не тратит» — пока лимит для всех моделей не исчерпан. Включается
  опцией `model_hint`, `install.sh --model-hint` или `UM_MODEL_HINT=1`.
- Все функции настраиваются в обоих режимах установки, и настройка действует
  везде, включая фоновый агент. В плагине появились опции `compact_warn`
  (порог подсказки о `/compact`), `statusline_model` и `subagent_model`
  (сегменты statusline), `interval` (интервал агента). У `install.sh` —
  флаги `--warn`, `--crit`, `--compact-warn` и `--interval`; `update.sh` их
  помнит. Раньше пороги для классической установки задавались только
  переменными, а их фоновый агент не видит. Раздел «Настройка» в README
  показывает, где задаётся каждая функция в каждом режиме.

### Fixed

- Интервал фонового агента, исправленный вручную в plist, как советовал
  README, тихо возвращался к 92 секундам: плагин перезаписывает plist на
  каждом старте сессии, `update.sh` — при обновлении. Теперь интервал —
  настройка (`interval` / `--interval`), и она сохраняется.
- Описание опции `launchd` в плагине говорило «каждые 5 минут» — с 0.9.0
  агент проверяет каждые 92 секунды.

## [0.10.0] - 2026-10-23

### Added

- Прогноз исчерпания ⏳: если при нынешнем темпе лимит кончится до сброса
  окна, приходит уведомление — «46% — при таком темпе кончится ~чт 14:00,
  сброс сб 10:00», одно на окно и раньше порога 80%. Темп берётся из истории
  замеров: для 5-часового окна — за последний час, для недели — за сутки (с
  ночами и перерывами). Пока данных мало, ниже 25% недели или если запас до
  сброса невелик, прогноз молчит. `status` показывает его у каждого окна
  («кончится ~17:10»).
- История замеров — `usage-history.<аккаунт>.jsonl` в каталоге состояния:
  строка при каждом изменении процентов и не реже раза в 30 минут, отдельно
  для каждого аккаунта, не больше 2 МБ. Новых запросов к API не добавляет —
  пишется то, что монитор и так получает.
- Темп недели: `status` показывает у недельных окон, где они были бы при
  равномерном расходе («по графику 38%»), а statusline — насколько неделя от
  него отклонилась: `7д 46% ▲8` (жёлтый) — расходуете быстрее, лимит кончится
  до сброса; `7д 20% ▼37` (голубой) — медленнее, часть лимита сбросится
  неиспользованной. Стрелка появляется от 5 пунктов. Если неделя отстаёт,
  `status` говорит, сколько пропадёт: «к сбросу ~34% (останется 66%)» —
  подписка оплачена, даже если не используется.
- Уведомление 💳 о платных usage credits: когда лимиты подписки кончились и
  начали тратиться деньги, и на 80%/95% лимита расходов. Сумма видна в
  `status`.
- `status` показывает расход недели по продуктам: «Claude Code 88%, чаты
  12%» — доли потраченного, а не лимита. Строка появляется, когда продуктов с
  расходом два и больше.
- Прогноз, уведомление о credits и темп в statusline выключаются в любой
  установке, и выключаются везде, включая фоновый агент: опции плагина
  `forecast`, `spend_alert`, `statusline_pace`, флаги `install.sh`
  `--no-forecast`, `--no-spend-alert`, `--no-statusline-pace` (`update.sh`
  их помнит) или переменные `UM_FORECAST=0`, `UM_SPEND_ALERT=0`,
  `UM_STATUSLINE_PACE=0`.
- `usage-monitor.sh doctor` и скилл `limit-alerts:doctor`: проверка установки
  по файлам, без запросов к endpoint, — токен в Keychain, аккаунт, возраст
  данных, пауза после ошибок, последняя неудачная проверка, история, фоновый
  агент, statusline, хуки, двойная установка, устаревшая сессия плагина.
  `doctor --notify` присылает тестовое уведомление.

### Changed

- Без `jq` команды `status` и `doctor` говорят, что его нужно установить,
  вместо молчания. Хуки и фоновый агент по-прежнему молчат.

### Fixed

- `status` писал «сброс: ?» у 5-часового окна, пока оно не открыто (после
  сброса окно начинается с первого сообщения). Теперь — «окно не открыто».
- Уведомления 🟡/🔴 о недельном лимите называли время сброса без дня —
  «сброс в 10:00», хотя до него могло быть до семи суток. Теперь — «сброс в
  сб 10:00», а дальше шести дней — дата.

## [0.9.3] - 2026-10-23

### Fixed

- Сессия, запущенная до обновления плагина, откатывала его обратно: на
  `/clear`, сжатии контекста и `--resume` её старый `SessionStart` копировал
  свои скрипты поверх новых и переписывал фоновый агент по старому шаблону, а
  следующая новая сессия возвращала всё назад. На живой установке так фоновый
  агент работал попеременно на 0.8.0 и 0.9.2: интервал прыгал между 300 и 92
  секундами, пауза после 429 то росла, то сбрасывалась. Теперь bootstrap,
  который старше уже установленной копии, ничего не трогает и просит
  перезапустить сессию. Выключить statusline или агент из старой сессии
  по-прежнему можно. Сессии, запущенные на 0.9.2 и раньше, исправление не
  затрагивает — их надо перезапустить один раз.

## [0.9.2] - 2026-10-15

### Fixed

- Пауза после ответа 429 не росла: endpoint лимитов присылает
  `Retry-After: 0`, монитор принимал это буквально и ждал минуту, после чего
  снова получал 429 — на живой установке так прошло 34 ответа подряд, а
  раньше в тот же день ещё 95. Теперь нулевой `Retry-After`, как и у самого Claude
  Code, считается отсутствующим: пауза 5 минут и удваивается до часа. В логе
  видно, что прислал сервер (`server Retry-After: 0`).

## [0.9.1] - 2026-10-15

### Fixed

- Переключение между аккаунтами (или организациями) выглядело для монитора
  как сброс окна: приходили ложные «♻️ Лимит сброшен (было 67%, сейчас 37%)»,
  предупреждения 🟡/🔴 перевзводились, а statusline могла показать цифры
  предыдущего аккаунта. Теперь всё привязано к текущему входу — аккаунт и
  организация из `~/.claude.json`: состояние уведомлений и пауза после ошибок
  хранятся отдельно для каждого аккаунта, кэш и общее наблюдение statusline
  помечены аккаунтом и для другого не используются, а резервные данные Claude
  Code берутся только своего аккаунта. Прежнее общее состояние переходит к
  первому аккаунту, который встретится.

## [0.9.0] - 2026-10-15

### Changed

- Фоновый агент проверяет лимиты каждые 92 секунды вместо 5 минут —
  уведомления о пороге и сбросе окна приходят быстрее, даже когда Claude Code
  закрыт. Уже установленный агент получит новый интервал сам: классическая
  установка — при `./update.sh`, плагин — при следующем старте сессии.

### Fixed

- Ответ 403 и 401 от endpoint лимитов теперь тоже включает паузу, как 429 (так
  же поступает и сам Claude Code). Раньше аккаунт, которому endpoint отвечает
  403 (встречалось у Team/организаций), опрашивался на каждом тике агента и
  каждый раз запускал фоновый `claude -p /usage`; теперь — одна попытка
  обновления через Claude Code в начале паузы.
- Statusline в простаивающем терминале показывала застывшие цифры: проценты
  из stdin Claude Code обновляет только по ответам API своей сессии, и работа
  в другом терминале, на другом устройстве или на claude.ai не была видна.
  Теперь каждое окно берёт более свежую из двух цифр — из stdin или из кэша с
  данными всего аккаунта (внутри окна расход только растёт, поэтому побеждает
  более поздний сброс, а для одного окна — больший процент), а устаревший кэш
  statusline обновляет сама, в фоне, не задерживая отрисовку
  (`UM_STATUSLINE_BG_REFRESH`, `UM_STATUSLINE_REFRESH_AFTER`).
- Несколько терминалов показывали разные цифры и делали каждый свой запрос.
  Работающие сессии видели в stdin каждая свой последний ответ API; теперь
  statusline делятся самым свежим наблюдением через общий файл, и все
  терминалы показывают одну цифру. Одновременные проверки (агент, Stop-хуки
  нескольких терминалов, фоновые обновления простаивающих statusline) делают
  один запрос на всех: остальные дожидаются его результата.
- Резервное обновление через `claude -p /usage` запускается не чаще раза в
  5 минут, какой бы ни была причина неудачи: без сети, при ответе 5xx или без
  токена в Keychain оно иначе стартовало бы на каждом 92-секундном тике агента.
- Statusline, работая от кэша, больше не показывает `0%` для окна, которого в
  ответе endpoint нет (например, у плана без 5-часового лимита), — такое окно
  просто не выводится.

## [0.8.0] - 2026-10-10

### Added

- Statusline показывает время сброса у окна, дошедшего до порога
  предупреждения: `5ч 84% ↻00:20`, а если сброс дальше суток — дату,
  `7д 96% ↻13.10`. Ниже порога строка остаётся прежней. Работает и для
  недельного лимита по модели; отключается `UM_STATUSLINE_RESET=0`.

## [0.7.0] - 2026-10-10

### Changed

- Statusline берёт проценты 5ч и 7д из собственного stdin: Claude Code сам
  передаёт их (`rate_limits`) по заголовкам последнего ответа API. Цифры в
  строке теперь актуальны на последний ход, а не отстают до 5 минут, и не
  зависят от endpoint лимитов (в том числе от его ответов 429). Кэш остаётся
  для недельного лимита по модели — его знает только endpoint, и он скрывается,
  когда его окно уже сбросилось, — и для начала сессии, пока ответа API ещё не
  было.

## [0.6.3] - 2026-10-10

### Fixed

- После ответа HTTP 429 проверки продолжали спрашивать endpoint лимитов на
  каждом хуке и каждом тике агента — и тем самым поддерживали ограничение
  частоты. Теперь живые запросы приостанавливаются: на `Retry-After`, если
  сервер его прислал, иначе на 5 минут с удвоением, но не больше часа. Пауза
  снимается первым успешным запросом, а `status` показывает, когда будет
  следующая попытка.
- Резервное обновление через `claude -p /usage` запускало хуки самого проекта
  внутри этой фоновой сессии: каждая неудачная проверка агента порождала ещё
  один запрос к endpoint. Теперь хуки внутри неё сразу завершаются
  (`UM_INTERNAL=1`).

## [0.6.2] - 2026-10-09

### Changed

- `usage-monitor.sh status` (и скилл `limit-alerts:status`) больше не молчит,
  когда свежие данные получить не удалось: строка версии печатается всегда,
  дальше — последний кэш с пометкой, насколько он устарел, а окна, которые с
  тех пор уже сбросились, помечены «(уже сброшен)». Без кэша — одна строка о
  том, что данных нет, со ссылкой на лог. Хуки и фоновый агент по-прежнему
  молчат, если данных нет: на устаревшие цифры они не реагируют.

## [0.6.1] - 2026-10-09

### Fixed

- Ответ HTTP 429 (слишком много запросов) от endpoint лимитов писался в лог
  как «токен, вероятно, истёк», что уводило диагностику не туда. Теперь лог
  различает 401/403 (токен), 429 (ограничение частоты, пройдёт само) и прочие
  коды.
- `uninstall.sh` удаляет оставшуюся блокировку `usage-monitor.lock`, если
  проверку прервали посреди обновления состояния.

## [0.6.0] - 2026-10-09

### Added

- Установка как плагин Claude Code — теперь основной способ.
  `/plugin marketplace add aquahitt/claude-code-limit-alerts`, затем
  `/plugin install limit-alerts@claude-code-limit-alerts`. Хуки регистрируются
  самим плагином, `~/.claude/settings.json` при этом не правится вообще.
- Настройки плагина через `userConfig`: язык, пороги предупреждения и
  критического уровня, выключатели уведомлений «требуется внимание», подсказки
  о `/compact`, statusline и фонового агента. Statusline и агент выключены по
  умолчанию — они пишут за пределы плагина, поэтому включаются явно.
  Скрипты читают `CLAUDE_PLUGIN_OPTION_*` только когда запущены из самого
  плагина: эти имена общие для всех плагинов и протекают в чужие хуки, так что
  классическая установка их игнорирует.
- Скиллы `limit-alerts:status`, `limit-alerts:setup` и
  `limit-alerts:uninstall`. Последний нужен потому, что отключение плагина не
  отменяет запись statusline и регистрацию launchd-агента.
- `scripts/plugin-bootstrap.sh` — хук `SessionStart`: зеркалит два скрипта,
  которым нужен стабильный путь, в `${CLAUDE_PLUGIN_DATA}/bin`, применяет
  включённые statusline и launchd и один раз предупреждает, если рядом
  работает классическая установка.

### Changed

- Каталог состояния резолвится через `UM_STATE_DIR` с откатом на
  `~/.claude/scripts`. Классическая установка попадает ровно туда же, куда и
  раньше. `CLAUDE_PLUGIN_DATA` в цепочке намеренно нет: эту переменную
  экспортирует тот плагин, чей хук выполняется, и она протекает в посторонние
  шеллы — классическая установка в сессии с любым включённым плагином иначе
  молча унесла бы своё состояние в чужой каталог.
- `generate_plist` принимает необязательные label, путь к скрипту и файл
  ошибок. `install.sh` и `update.sh` вызывают её без изменений — проверено
  побайтовым сравнением сгенерированного plist до и после. Агент плагина живёт
  под отдельным label `com.claude.usage-monitor.plugin`, поэтому две установки
  никогда не спорят за один plist.

### Fixed

- Одно и то же предупреждение о лимите могло прийти дважды, если Stop-хук,
  `SessionStart` и launchd-агент запускались одновременно: оба запуска читали
  одно состояние и оба считали порог новым. Теперь обновление состояния идёт
  под блокировкой (`usage-monitor.lock` в каталоге состояния); запуск, который
  не дождался её за 5 секунд, просто выходит — держатель блокировки сообщает то
  же самое. Блокировка старше минуты считается брошенной и снимается.

## [0.5.0] - 2026-08-25

### Removed

- Авто-продолжение сессии после сброса лимита целиком: скрипт
  `auto-resume.sh` и его состояние `auto-resume-state.json`, уведомление 🚫 с
  командой продолжения, автозапуск воркера в новом окне терминала, флаги
  `install.sh` `--no-auto-resume` и `--auto-resume-autostart`, переменные
  `UM_BLOCK_PCT`, `UM_SESSION_TTL`, `UM_RESUME_PROMPT`, `UM_RESUME_MAX_WAIT`.

  Причина: Claude Code 2.1+ делает это сам — тумблер «Continue automatically
  at usage limit» в `/config` (`autoContinueAtUsageLimit` в
  `~/.claude/settings.json`). Встроенное продолжение не требует ни выхода из
  сессии, ни второго терминала, ни `--resume`, а внешний воркер требовал всего
  этого — и, работая рядом со встроенным, продолжал бы один разговор дважды,
  двумя процессами на один `session_id`.

  `install.sh` и `update.sh` при обновлении удаляют оставшиеся от прежних
  версий `auto-resume.sh`, файл состояния и lock-файлы. Мониторинг лимитов,
  пороги 🟡/🔴, уведомление о сбросе окна, statusline и подсказка о `/compact`
  не изменились; `usage-monitor.sh limits` сохранён.

## [0.4.0] - 2026-08-21

### Added

- `auto-resume.sh`: дожидается сброса исчерпанного лимита и продолжает
  прерванную сессию интерактивно (`claude --resume`), перепроверяя реальные
  лимиты после `resets_at`, а не доверяя одному только времени — недельный
  лимит регулярно переживает пятичасовое окно.
- `usage-monitor.sh` теперь записывает активную сессию из stdin хука
  (`session_id`, `cwd`, `transcript_path`) в `auto-resume-state.json` и
  уведомляет один раз за окно, когда лимит сессии исчерпан, копируя команду
  продолжения в буфер обмена.
- `usage-monitor.sh limits`: машиночитаемый снимок лимитов
  (`kind|percent|resets_at|scope`), без заголовка и локализации; учитывает
  `UM_CACHE_TTL=0` для живого запроса без кэша.
- `compact-advisor.sh`: хук `Stop`, подсказывающий удачный момент для
  `/compact` — контекст выше `UM_COMPACT_WARN` (по умолчанию 70%), ход
  закончился без `tool_use`, и нет незакрытых задач. Хук не может выполнить
  `/compact` сам — это осознанно только сигнал.
- Флаги `install.sh`: `--no-auto-resume`, `--auto-resume-autostart`,
  `--no-compact-advisor`, `--auto-compact-window <токены>` (100000–1000000,
  записывается в `~/.claude/settings.json`).
- `~/.claude/scripts/.limit-alerts-options` запоминает выбор, сделанный при
  установке, чтобы `update.sh` никогда не включал фичу, от которой
  пользователь отказался.
- Statusline: модель сессии, уровень `effort` и заполненность контекста —
  берутся из собственного stdin statusline (без лишнего I/O), плюс модель
  работающего субагента, когда она отличается от модели сессии — читается из
  `<проект>/<session_id>/subagents/` и считается «живой» по времени
  изменения транскрипта (`UM_SUBAGENT_TTL`, по умолчанию 180 с). Несколько
  субагентов на одной модели схлопываются в `⇢ 2× Haiku 4.5`. Рядом
  показывается модель встроенного советника (`/advisor`, ключ `advisorModel`),
  когда её семейство отличается от модели сессии — `adv Fable`; отключается
  через `UM_STATUSLINE_ADVISOR=0`. Модели сравниваются целиком, когда обе
  стороны несут версию (Sonnet 4 и Sonnet 4.5 остаются разными), и по семейству
  — только когда одна из сторон голый алиас без версии. Это же убирает ложное
  `⇢` для субагента, чья модель известна лишь по алиасу из `meta.json`.
- Флаги `install.sh` `--no-statusline-model` и `--no-subagent-model` —
  каждый запоминается в `.limit-alerts-options` и вшивается в установленный
  скрипт так же, как `--lang` раньше.

### Changed

- Statusline: недельный лимит с привязкой к модели теперь с префиксом
  (`нед.` / `wk`), чтобы `Fable 4%` нельзя было принять за модель, которая
  работает прямо сейчас, теперь когда рядом на строке может стоять настоящее
  имя модели.
- `uninstall.sh` удаляет новые скрипты, файлы состояния и lock-файлы, а
  `autoCompactWindow` убирает только если его выставил этот же проект.

### Fixed

- `update.sh` больше не теряет язык, выбранный при установке: он копирует
  скрипты из репозитория поверх установленных, а выбор `--lang` вшит именно
  в установленные копии, так что после любого обновления уведомления молча
  возвращались к русскому. Теперь выбор восстанавливается из
  `.limit-alerts-options`.
- Флаги со значением (`--lang`, `--proxy`, `--auto-compact-window`) больше не
  завершаются молча с кодом 1, если значение не указано — печатается
  внятное сообщение.
